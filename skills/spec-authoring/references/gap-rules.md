# 缺口识别与结构化改写规则(gap rules)

[#114](https://github.com/olaola-projects/ai-native-issues/issues/114) 交付物:Phase 2 的判定
与改写依据。对照四部分模板扫描原始资料与已实例化的四份 spec,把每条缺口判入下方四类之一,
产出 `00-gap-report.md` 缺口报告,并按「改写守则」**就地改写**四份 spec。

> 借鉴声明:缺口分类扫描与限量问询的流程思想借自 spec-kit `/speckit.clarify`(只借思想,
> 不引入其命令链);完整复用边界见 `upstream-reuse.md`。

## 四类判定 × 输出动作

| 类别 | 判定标准(要点) | 输出动作 | 与 CL-### 的关系 |
|---|---|---|---|
| **缺失** | 某父票要点/模板章节在原始资料中完全无着落 | 报告记 GAP;spec 对应章节留结构占位 | **必开新 CL**(问题 =「该要点的内容是什么」) |
| **含糊** | 有着落但不可验证:无数值/单位/边界、无 RFC 2119 情态、主观形容、开放列表 | 报告记 GAP;**改写为可度量表述**(值不明用带编号的 `<待定,CL-###>` 占位) | 补值需要业务事实才开 CL;纯措辞问题改写即闭环 |
| **不自洽** | 资料内部两处冲突,或资料与 04 框架约束冲突 | 报告「不自洽对照」行:并列引用双方原文+出处,**不得擅自裁决** | **必开新 CL**,写成带选项的裁决题(A / B / 其他) |
| **细节不足** | 有着落、方向明确,但深度不够驱动生成 | 报告记 GAP;**改写补出结构骨架**(表格行、Scenario 骨架、字段清单) | 骨架中每个事实空洞开一个 CL |

### 缺失(missing)

- **判定**:以 `coverage-map.md` 人读对照表的 27 个父票要点 + 各章「本章自检」为清单逐条对照;
  资料通篇找不到该主题的任何信息即为缺失(整章缺失与要点级缺失都算,粒度记到要点)。
- **动作**:spec 对应章节保留模板结构,填 `[NEEDS CLARIFICATION(CL-###): <该要点问题>]`;
  问题写成**最小问题集**(owner 答完即可填章),不写开放式的「请补充 XX 章」。
- **例**:资料没提任何监控要求 → 03 §3 整章缺失,CL 问「上线后要看哪些指标、什么阈值告警」。

### 含糊(vague)

- **判定**:主题有着落但写法不可验证 —— 无数值/单位/边界条件(「加载要快」)、无 RFC 2119
  情态(分不清 MUST 还是 MAY)、主观形容(「体验流畅」「奖励丰厚」)、开放列表(「等」「之类」)。
- **动作**:改写为可度量表述;资料能推出的值直接填并注来源;推不出且需 owner 供值的,
  占位**必须挂编号**、写作 `<待定,CL-###>`(与 SKILL.md「不允许残留无编号未知项」同一标准,
  裸 `<待定>` 不允许残留);纯措辞收紧(补情态词、收拢开放列表)改写即闭环、不留占位、不开 CL。
- **例**:「加载要快」→「首屏加载 SHALL ≤ `<待定,CL-00N>` s(03 §1.1 性能预算)」,CL 问数值。

### 不自洽(inconsistent)

- **判定**:资料内部两处冲突(同一数值两个值、状态机不可达/死循环、FR 与非目标打架),
  或资料与 04 框架约束/硬性红线冲突(要求引入被禁的依赖等)。
- **动作**:报告 §3「不自洽对照」并列引用**双方原文与出处**;spec 正文不选边,冲突位置填
  `[NEEDS CLARIFICATION(CL-###): A 还是 B?]`;裁决题给出可选项(A / B / 其他),**不得擅自裁决**。
- **例**:活动页写「每日上限 3 次」、规则页写「每日 5 次」→ §3 记对照,CL 让 owner 拍板。

### 细节不足(insufficient detail)

- **判定**:有着落、方向明确,但深度不够下游生成直接消费 ——「发金币」但无上限/保底/溢出
  规则;有屏幕清单但无空态/加载态/错误态;有接口但无字段与错误码。
- **动作**:按模板结构补出**骨架**(表格行、`#### Scenario:` 骨架、字段清单),骨架中每个
  事实空洞逐一开 CL —— 骨架本身不算虚构(结构是模板约定),**往骨架里填未给出的业务值才是虚构**。
- **例**:「通关发金币」→ 01 §4.3 补奖励规则表(触发/数量/每日上限/溢出处理),数量与上限各开 CL。

## GAP-### 与 CL-### 的编号关系

- **GAP-###** 是缺口报告的行号:四类全覆盖,从 GAP-001 起按发现顺序递增,只出现在 00 报告;
- **CL-###** 是写进 spec 正文的待澄清标记:只给需要 owner 提供业务事实的项,编号续 Phase 1
  的全局序列(四份文件 + 后续轮次统一递增),**不换号、不重排、不复用**;
- 一条 GAP 挂 **0..n** 个 CL(纯改写闭环的 GAP 挂 0 个);反向同样成立:**一个 CL 可被多条
  GAP 共挂** —— 缺口粒度记到要点,但问题以**最小问题集**为准:能一问解决多条 GAP 就共挂
  一问(如「有无图形界面」一问门控 02 多章),不给 owner 发重复问题;
- **优先复用,再开新号**:Phase 2 扫描命中的问题若 Phase 1 已开 CL,GAP 行直接引用既有编号,
  不重复开号(「必开新 CL」指该问题**尚无 CL** 时);确需新 CL 且其裁决会使旧 CL 失效的,
  在报告该行注明「CL-新 裁决后关闭 CL-旧」;
- 报告与 spec 的对账:未决 CL 计数 = spec 中未解决的 CL 编号数(**按编号去重**)= 报告
  open 行所挂 CL 的**去重**编号数;对账扫描**以 §2/§3 的 CL-### 列为准** —— 证据/动作栏
  对历史 CL 的引用不计入;
- Phase 2 改写即闭环、无待决业务事实的 GAP,状态直接标 `resolved(R0)`(R0 = Phase 2 本轮),
  不计入未决。

## 改写守则(结构化改写 = 就地更新 01–04)

1. **不虚构**:改写只做「重排 + 结构化 + 收紧措辞」,不发明资料没给的业务事实、数值或约定
   (SKILL.md 硬规则)。
2. **散文 → 结构**:把资料中的散文需求拆成 FR-### 行(RFC 2119 情态)、把规则改写成
   `### Requirement:` + `#### Scenario:`、把验收性描述改成 Given-When-Then 并回链 FR。
3. **含糊 → 可度量**:按「含糊」类动作执行;每处改写在报告 §4 记一笔。
4. **细节不足 → 骨架**:按「细节不足」类动作执行;骨架空洞逐一挂 CL。
5. **不自洽 → 不裁决**:按「不自洽」类动作执行;spec 里绝不悄悄选边。
6. **就地改写,不出平行文稿**:直接更新落点的 01–04(落点在挂载仓时走该仓自己的 branch/PR,
   diff 即改写稿),不建平行的「改写版」文件或提案目录;每份文件的实质改动在报告 §4 记摘要。
7. **checklist 如实复核**:改写后真正到位的章节才补勾;不得为了报告好看而勾选。
